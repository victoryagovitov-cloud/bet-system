# ОТЧЕТ: ТОНКИЕ МЕСТА И ОПАСНОСТИ В СИСТЕМЕ

## КРИТИЧЕСКИЕ ПРОБЛЕМЫ (ВЫСОКАЯ СЕРЬЕЗНОСТЬ)

### 1. ПАРСИНГ ДАННЫХ

#### 1.1. Парсинг минут в разных форматах
- **Проблема**: Минуты могут приходить как '05:46', '5', 'HT', 'FT', '45+2' и т.д.
- **Местоположение**: `graphql_live_analyzer.py`, `graphql_basketball_analyzer.py`
- **Риск**: Матч может быть неправильно отфильтрован
- **Пример**: Матч на 5 минуте может быть пропущен, если парсинг вернет None
- **Решение**: Улучшить `_parse_minute_value()` для обработки всех форматов

#### 1.2. Парсинг счета в разных форматах
- **Проблема**: Счет может быть в разных полях: `game_score`, `result_score`, `game_state`
- **Местоположение**: `graphql_basketball_analyzer.py`, `graphql_handball_analyzer.py`
- **Риск**: Матч может быть пропущен, если счет не найден
- **Статус**: Частично исправлено (баскетбол теперь проверяет result_score)
- **Решение**: Унифицировать парсинг счета для всех видов спорта

#### 1.3. Отсутствие статистики (None значения)
- **Проблема**: Статистика может быть None, но код может не обработать это
- **Местоположение**: Все анализаторы
- **Риск**: Ошибка при расчете dominance_score (деление на ноль, операции с None)
- **Пример**: `points[0]` может быть None, но код делает `float(points[0])`
- **Решение**: Добавить проверки на None перед использованием

### 2. КОЭФФИЦИЕНТЫ

#### 2.1. Отсутствие коэффициентов
- **Проблема**: Коэффициенты могут отсутствовать для матча
- **Местоположение**: `_get_leader_odds()`
- **Риск**: Матч будет отфильтрован, даже если он хороший
- **Пример**: Матч с dominance=10, но нет коэффициентов - не попадет в отчет
- **Решение**: Улучшить fallback логику или разрешить матчи без коэффициентов

#### 2.2. Коэффициент может быть None после получения
- **Проблема**: `odds.value` может быть None, но код может не проверить
- **Местоположение**: `_select_top_*_matches()`
- **Риск**: Ошибка при сравнении `odds.value <= PRIMARY_MAX_ODDS`
- **Пример**: `if odds.value <= 1.10` может упасть, если `odds.value is None`
- **Решение**: Добавить проверку `if odds and odds.value is not None`

### 3. API И СЕТЬ

#### 3.1. Таймауты API Scores24
- **Проблема**: API может не отвечать или отвечать медленно
- **Местоположение**: `scores24_graphql_client.py`
- **Риск**: Анализ может зависнуть или упасть
- **Пример**: `fetch_match_stats()` может зависнуть надолго
- **Решение**: Добавить таймауты для всех API запросов

#### 3.2. Отсутствие обработки ошибок API
- **Проблема**: Некоторые вызовы API могут не иметь try/except
- **Местоположение**: `scores24_graphql_client.py`
- **Риск**: Система может упасть при ошибке API
- **Пример**: `fetch_live_matches()` может упасть, если API недоступен
- **Решение**: Обернуть все API вызовы в try/except

### 4. БАСКЕТБОЛ (НОВЫЙ ВИД СПОРТА)

#### 4.1. Счет используется как очки, если статистики нет
- **Проблема**: Если нет статистики points, используется счет
- **Местоположение**: `graphql_basketball_analyzer.py`
- **Риск**: Может быть неточным для расчета dominance
- **Пример**: Счет 50:40, но реальная статистика может быть другой
- **Решение**: Тестировать на реальных данных, возможно улучшить формулу

#### 4.2. Минимум 15 минут может быть слишком строгим
- **Проблема**: Многие матчи отфильтровываются как слишком рано
- **Местоположение**: `graphql_basketball_analyzer.py`
- **Риск**: Мало матчей будет найдено
- **Пример**: Матчи на 5-10 минутах отфильтровываются
- **Решение**: Рассмотреть снижение до 10 минут или динамический порог

## СРЕДНИЕ ПРОБЛЕМЫ

### 5. ДЕДУПЛИКАЦИЯ

#### 5.1. Окно дедупликации 4 часа
- **Проблема**: Матч не будет отправлен повторно в течение 4 часов
- **Местоположение**: `_filter_duplicates()`
- **Риск**: Если матч продолжается > 4 часов, он может быть отправлен повторно
- **Пример**: Матч на 60-й минуте, потом на 75-й - может быть отправлен дважды
- **Решение**: Учитывать slug + timestamp для более точной дедупликации

#### 5.2. Slug может измениться
- **Проблема**: Slug матча может измениться между запросами
- **Местоположение**: `_get_recent_slugs()`
- **Риск**: Один и тот же матч может быть отправлен дважды с разными slug
- **Решение**: Использовать комбинацию slug + teams + timestamp

### 6. ВРЕМЯ И ТАЙМЗОНЫ

#### 6.1. Смешение timezone-aware и timezone-naive datetime
- **Проблема**: Некоторые datetime могут быть без таймзоны
- **Местоположение**: `system_monitor.py`, `generate_live_report.py`
- **Риск**: Ошибка при сравнении времени
- **Статус**: Частично исправлено (добавлены .replace(tzinfo=TZ_MOSCOW))
- **Решение**: Убедиться, что все datetime timezone-aware

#### 6.2. Парсинг минут из строки
- **Проблема**: Минуты могут быть в формате '05:46', '5', 'HT', '45+2'
- **Местоположение**: `_parse_minute_value()`
- **Риск**: Неправильный парсинг может привести к неправильной фильтрации
- **Решение**: Улучшить парсинг для всех форматов

### 7. ФИЛЬТРАЦИЯ

#### 7.1. Логика 'ИЛИ' в фильтрах
- **Проблема**: Матч может пройти через 'ИЛИ', даже если dominance низкий
- **Местоположение**: `_select_top_matches()`, `_select_top_tennis_matches()`
- **Риск**: Слабые матчи могут пройти фильтры
- **Пример**: dominance=5.9 (не проходит), но xG_diff=0.3 и minute=60 - пройдет
- **Решение**: Ужесточить требования для 'ИЛИ' условий

#### 7.2. Динамические требования по времени
- **Проблема**: Требования меняются в зависимости от минуты
- **Местоположение**: Все `_select_top_*_matches()`
- **Риск**: Резкий переход требований (29-я минута = 6.0, 31-я = 5.0)
- **Пример**: Матч на 29-й минуте требует dominance=6.0, на 31-й - только 5.0
- **Решение**: Плавный переход требований

### 8. DOMINANCE_SCORE

#### 8.1. Операции с math.nan
- **Проблема**: Если статистики нет, значения могут быть math.nan
- **Местоположение**: Все анализаторы
- **Риск**: Операции с nan дают nan, что может сломать сравнения
- **Пример**: dominance_score может быть nan, но сравнивается с числом
- **Решение**: Проверять на nan перед использованием

#### 8.2. Деление на ноль
- **Проблема**: При расчете pace или других метрик может быть деление на ноль
- **Местоположение**: `graphql_handball_analyzer.py`, `graphql_basketball_analyzer.py`
- **Риск**: ZeroDivisionError может упасть система
- **Пример**: `pace = total_score / minute_numeric`, если `minute_numeric = 0`
- **Решение**: Добавить проверку на ноль перед делением

#### 8.3. Слишком большой бонус от score_factor * time_factor
- **Проблема**: Бонус может маскировать слабую статистику
- **Местоположение**: `graphql_live_analyzer.py`
- **Риск**: Матч с плохой статистикой может пройти из-за большого бонуса
- **Пример**: Матч 2:0 на 80-й минуте: бонус = 3.56, маскирует слабую статистику
- **Решение**: Ограничить максимальный бонус или уменьшить вес

### 9. ПЛАНИРОВЩИК

#### 9.1. Таймаут 600 секунд (10 минут)
- **Проблема**: Если анализ занимает > 10 минут, он прерывается
- **Местоположение**: `auto_cycle_scheduler.py`
- **Риск**: Анализ может быть прерван, матчи не будут отправлены
- **Пример**: Много матчей или медленный API - анализ может не завершиться
- **Решение**: Увеличить таймаут или оптимизировать анализ

#### 9.2. Lock файл может остаться после краша
- **Проблема**: Если планировщик упал, lock файл может остаться
- **Местоположение**: `auto_cycle_scheduler.py`
- **Риск**: Новый планировщик не запустится
- **Статус**: Частично исправлено (watchdog проверяет, но не всегда работает)
- **Решение**: Улучшить проверку stale lock файлов

#### 9.3. Grace period 7 минут
- **Проблема**: Если планировщик пропустил слот, он попытается запустить в течение 7 минут
- **Местоположение**: `auto_cycle_scheduler.py`
- **Риск**: Может быть слишком поздно для анализа
- **Пример**: Слот 21:00 пропущен, попытка в 21:05 - матчи могут уже закончиться
- **Решение**: Уменьшить grace period или улучшить логику пропущенных слотов
